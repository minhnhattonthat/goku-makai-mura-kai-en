# Text

Three sources. Everything else on screen is a texture (`docs/re/graphics.md`).

| Source | Size | How it's drawn |
|---|---|---|
| `.bms` message files | 31 KB, 305 unique strings, ~15k JP chars | `jfont_00`, by the game's text engine |
| UTF-8 strings in `*.PRX` | 23 strings | PSP save dialog (system font) |
| Textures | see `graphics.md` | pre-drawn |

## .bms message files (verified: decoded script reads as sentences, 0 unknown codes; `tools/bms.py`)

Tree: `memstick.kpd/memstick/memstick.bms`, `movie.kpd/movie/mv00-06.bms` (subtitles), `play_res.kpd/2d/a02/a02.bms` (pause menu),
`a10.bms` (options), `st_select.kpd/2d/a30/a30.bms`, `s0506 s0507 s0600 s0700 s0800_stg.kpd/.../sNNNN.bms` (stage messages).
GOKUMAKAI only: `a03.bms` (15 KB, equipment and item names and descriptions), `a04.bms`.
9 of the 16 shared files are byte-identical between the games; memstick, mv04, a02, s0507, s0600, s0700 and s0800 differ. Translate
shared strings once.

Format: `u32 count`, `u32 offset[count]`, then the strings, each ending in 00. **Slice by the next offset, never scan for NUL**:
`80 00` is the glyph あ.

Pointers: absolute offsets from file start, in that one table. No code points into the strings: **verified** by the marker
build (2026-11-12), where every file is rebuilt with new offsets and lengths and every box shows its own id.

## Encoding (verified on known strings: はい, いいえ, ゲームデータ)

Stream bytes:
- `80-87 xx`: two-byte glyph.
- `09-7F`: one-byte glyph.
- `00-08`: control codes.

`jfont_00.bft` maps code -> cell of `jfont_00.gim` (identical in both games): at 0x2c a 128-entry page for one-byte codes, then 8
pages of 256 entries (u32 offsets at 0x0c) for lead bytes 80-87. Entry = 5 u16 `{0, x, y, w, h}`. Cells are 18x16.
**The ASCII glyphs have w=12, kana and kanji w=18.** `w` is both the sheet rect's width and the advance (**verified**
2026-11-12: a bft with trimmed rects draws proportional text, centring included), so the variable-width font is bft edits only.

`tbl/jp.tbl` is generated by `tools/mk_tbl.py`, from the bft plus the glyph rows read off the font sheet. Half space is `70`, full
space `800F`. Entries past y=432 / x=504 point at cells the 512x512 sheet doesn't have; the script uses none of them.
Codec: `tools/tbl.py` (from the skill); bytes 00-08 are table lines `{end} {n} {02}..{06} {c:1} {08}`.

**Kanji verified by eye** (2026-11-12, `tools/fontcheck.py --sheet`, every kanji row 10-25 against the table): one misread,
row 21 col 27 is 揃 (was 捕: 捕う for 揃う). 必 and 心 were already right. Template matching against MS Gothic doesn't work on this
bold, outlined font (every cell matched a dense wrong kanji); read the sheet.

**Aliases:** several codes point at one cell: digits 09-12 and 71-7A, b-g at 4A-4F, w-z at 7B-7E, three × cells, a few kana and
kanji. No character is used under two codes in either game or the USA text, so `mk_tbl.py` lists the used code first (71-7A,
82A8) and the encoder picks it; an unused alias would decode as `[XX]` bytes and still roundtrip.

**USA font** (`work/us/font`): same bft entries and cell layout, restyled glyphs, so `tbl/jp.tbl` decodes the USA text as is.
Cell 80D7 `Ⓚ` draws "KB" and 80D4 `Ⅿ` draws "MB" in both fonts.

The font already holds A-Z, a-z, 0-9 and punctuation, so English needs no new glyphs for a start.

**The font both games ship with (phase 5, D11):** the USA `jfont_00.gim` as is, and its bft through `tools/vwf.py`: every ASCII
letter and mark (codes 10-29, 30-49, 50-61) gets x = its first ink column, w = ink width + 1 px; digits 71-7A all get one width
(10) so numbers line up; space 70 is 5 px. Kana, kanji and fullwidth cells are untouched. `build.font_files()` makes it from the
USA disc at build time; box budgets in that font: `docs/re/boxes.md`.

## script/ (phase 4, `tools/script.py`; roundtrip + coverage in `tests/test_script.py`)

One JSON per message file, per game: `script/re/` (Kai), `script/go/` (original), plus `prx.json` for the save-dialog strings.
Row: `id` (`a02:4`, `prx:0x349c64`), `jp`, `us`, `same`, `max` (PRX slot bytes), `en`, `status`, `notes`. Newlines are real `\n`.
- `official`: the USA disc's string at the same file and index (D10); en is prefilled with it. Indexes align in every file;
  memstick has 12 strings against the USA's 11, the 12th (index 11, the "other disc's save" notice) has no USA text.
- `inherit`: Kai row whose jp equals an original-game row (`same` names it); it takes that row's en. This also gives Kai's
  English-only boss names the USA spellings (Red Arimmar -> Red Devil).
- `keep`: no kana or kanji (Kai a02:24-34 digit strings, `０－０`): inserted as is. `empty`: empty strings.
- `new`: to translate. 37 rows, ~1,140 JP chars: Kai's own lines (s0507, s0600-0800 witch lines, mv04:13, memstick:11), both
  PRX tables (the USA EBOOT is encrypted, so no official stage names from it yet), and a03:142, where the USA text left a
  Japanese line.
- Coverage: every .bms in both datapacks; `bms.build(parse(file)) == file` for each, so the offset table and strings are the
  whole file; every string roundtrips with no `[XX]`; no Japanese UTF-8 (3+ chars) in either PRX outside the save region.
- `script.py dump` refreshes jp/us/same from the dumps and keeps any en that differs from the USA prefill (status
  `recheck` when its jp changed).

## PRX strings (UTF-8, NUL-terminated, fixed slots)

REGOKUMAKAI.PRX 0x3495a0-0x349904, GOKUMAKAI.PRX 0x349b30-0x349e80 (`script.PRX`, file offsets). Save title `極魔界村 改セーブデータ`, detail lines with
`%02d %d %s` (keep count and order), and about 20 stage/location names. Slots are 4-byte padded, usually 24-28 bytes, so the English
names are tight. Pointer table (phase 7): u32 words at go 0x351988-0x351a14, re 0x351488-0x351514, value + 0x80 = file offset,
one R_MIPS_32 reloc each; every row has its pointer(s) there and nowhere else (no lui/addiu pair, no mid-string pointer;
`5 暗黒の大魔宮殿` has 7). `script.prx_patch` keeps a string in its slot when it fits, else moves it into another slot's free
tail (4-aligned, like the compiler's) and rewrites its words; the titles and Dark Astaroth's Chamber move. Proven in game:
the save's PARAM.SFO and the load list show the full moved titles.

One **Shift-JIS** string sits outside the region: `新規作成データ` (the save utility's new-data entry title) at re 0x349ad0,
go 0x34a070 (`script.PRX_SJIS`), loaded by lui/addiu at re 0x41a98, go 0x42eb0 right after the new-data icon paths. No table
word: written in place only (15 bytes before the next word): "New Save Data". `script.sjis_runs` (NUL-bounded, 4-aligned,
3+ kana/kanji, not valid UTF-8) finds exactly this one per PRX; `script.py check` and diffcheck fail on any other.
PPSSPP draws its own "NEW DATA" there, so no emulator shot shows it.
